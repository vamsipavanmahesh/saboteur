M2’s byte ranges are sound. M4 is wired through the score and is mislabeled in the report text.

## 1. Parallel workers

**Death detection hangs.** [code] `collect` treats a closed results pipe as worker death and has no timeout (`worker_pool.rb:58-68`). Every mutant is a `fork`, and `fork` keeps the worker’s pipe ends (`worker_pool.rb:116-123`, `supervisor.rb:94`). `O_CLOEXEC` does not apply to `fork`. If the worker dies while a descendant still holds the results write end, `IO.select`/`gets` never sees EOF and never reaches `stop`’s 5s kill (`worker_pool.rb:137-143`). Ctrl-C is the same window: the worker inherits the parent trap, `exit` becomes `SystemExit`, `serve` catches it and `exit!`s (`supervisor.rb:65-69`, `worker_pool.rb:125-126`) without killing the mutant. The parent’s `ProcessTree` has not been polling that grandchild, and `setpgid(0,0)` (`supervisor.rb:108`) breaks the pgid fallback (`process_tree.rb:66-69`). On Linux the subreaper flag is not inherited, so the orphan is reparented to the top-level process (`supervisor.rb:253-259`), which does not know the pid.

**Rails databases.** [code] Copies are made for every test config (`rails.rb:52-57`), then the worker calls `Base.establish_connection` on `test_configs.first` only (`rails.rb:62-67`). Cache, queue, cable, and `connects_to` pools stay on the shared test database. `TEST_ENV_NUMBER` is set after boot (`worker_pool.rb:117-118`), so Rails will not suffix names that were already loaded. Worker 0 never enters `start_worker`. Postgres `CREATE … TEMPLATE` runs only after this process’s pools are disconnected (`rails.rb:97-103`); any other session on that database makes the run raise, and `DROP DATABASE` removes `app_test2`, `app_test3`, and so on. The SQLite branch copies one file and does not disconnect or take `-wal`/`-shm` (`rails.rb:104-105`). `after_fork` only disconnects (`rails.rb:120-122`). `rails_spec.rb` covers naming and `local_host?` only. Pools are still forked after a thread warning (`engine.rb:98-102`); a lock held by a non-forking thread deadlocks checkout.

**Other.** [code] `assign` can raise `EPIPE` if `on_start` has already closed the command pipe (`worker_pool.rb:84-89`, `119`), and that item has already been removed from the queue. `JSON.parse` in `collect` is unrescued. `jobs` is not part of `VERDICT_INPUTS` (`engine.rb:12-13`), so a parallel verdict is reused on a later serial run (`result_cache.rb:46-54`). Result order is by subject index (`distribution.rb:24-27`); the dry-inflector run matched (`docs/validation/phase-2-gems.md:60-63`). There is no process-wide memory cap: each worker may grow `max_memory_mb`.

[doc] `docs/status.md:40` still says Phase 5 needs an explicit go, and `:87-88` says Rails reconnect is Phase 4 work. `3ec138e` already ships `prepare_workers`.

## 2. M2 operators

[code] Swaps edit `message_loc` only; `true`/`false` replace the whole call (`builtin.rb:145-149`). Connectors replace the whole `And`/`Or` node with `operand.slice` (`builtin.rb:173-175`), so the operand’s own parentheses stay and the re-parse check drops invalid text (`candidates.rb:47-49`, `builtin_spec.rb:99-103`). Offsets are file offsets from a full-file parse (`subject_finder.rb:19`, `builtin.rb:221-226`). An unparenthesized operand is at least as tight as the connector, and a parenthesized connector is a `ParenthesesNode` outside that edit, so dropping the old extra parentheses is consistent with Ruby’s grammar. The connector set is three mutants, not Just’s four: `&&` → `==` and `||` → `!=` are absent (`builtin.rb:34-36`). `a.==(b)` is skipped because `binary?` requires no call operator (`builtin.rb:158-160`).
