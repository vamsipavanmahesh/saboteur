saboteur vs mutineer: benchmark evaluation

Note: measured at 2b6ec02, before the coarse-survivor gate was removed and before the rebaseline. Counts and times are historical; a rerun is pending.

2026-10-10 · saboteur 0.1.0 (commit 2b6ec02 engine) vs mutineer 1.6.0 · by Vamsi Pavan Mahesh Gunturu

This is not an exhaustive benchmark. In Results 1-5, each configuration ran once, on sampled files from four projects, on one macOS machine. Result 6 is separate: 30 paired runs on a Linux sandbox. Everything here was measured before the coarse-gate removal and is historical. Every number is indicative, not a statistical result. The scripts and raw data are in bench/vs-mutineer, so anyone can rerun or extend it.

saboteur and mutineer are two open-source tools that measure how good a Ruby project's tests are. We ran both on the same four RSpec projects and checked their answers against ground truth. saboteur came out ahead on Rails support and speed, and its kill-checking sample found no fake kills (a sample check, not a ranking); mutineer came out ahead on memory, choice of change types and CI features.

Verdict

saboteur wins 3 of 7 ranked metrics, mutineer wins 2, and 2 are ties. The two trust rows are sample checks and are not ranked. The most notable finding is: on lobsters, 8 of mutineer's kills that we hand-checked were not caught by any test. That is a check of 8 identical mutants, not a measure of either tool's overall accuracy.

Glossary

Mutation testing
Checking how good tests are by making small deliberate changes to the code and seeing whether the tests notice.
Mutant
One such change, for example a < b changed to a <= b, or one line removed.
Killed (caught)
At least one test failed with the mutant in place. The tests noticed.
Survived (missed)
Every test still passed with the mutant in place. This points to a gap in the tests.
Fake kill
A mutant reported as killed when the same tests also fail without the mutant. The failure came from something else, such as leftover test data. A crash can also be a legitimate kill when the mutant causes it. A fake kill hides a real gap.
No coverage
No test runs the changed line, so the mutant is not tested at all.
Timeout
The tests ran past the time limit, often because of an endless loop. The current saboteur counts a timeout as detected in the score.
Error
The tool could not reach a clean verdict. saboteur also uses this when a killing test fails even without the mutant.
Mutation score
Current saboteur: (killed + timeout) / (killed + survived + timeout). The scores on this page come from the measured version and may use a different definition. Comparable only between runs with the same set of mutants.
Operator
A kind of change a tool makes, for example removing a statement or flipping a comparison.
Defaults, matched
Defaults: each tool's own change types. Matched: the closest common set, so both tools test similar changes.
Worker
One parallel process running mutants.
Actionable, equivalent, noise
Labels for missed mutants. Actionable: a test should catch it. Equivalent: the change cannot alter behaviour. Noise: it changes behaviour, but not in a way worth testing.

Result 1: fake kills

mutineer reported fake kills on lobsters; saboteur had none in its sample.

mutineer scored 100% on the three lobsters models and named no killing test for any of its 91 kills. saboteur reported the same 8 mutants as missed, which is correct. saboteur also refused 3 of its own kills, because the killing test failed even without the mutant (leftover test data). Environment and method

  • Candidate: saboteur at d2b7abb336eae53ec8cd5a71c111f9daef66218a (merge of PR #4, "Pack the heap at fork boundaries"). Baseline: 32c0f21bdcbc059ac5938ae7630eb117442cd5fc, the first code-change ancestor; 32c0f21..d2b7abb^ is doc-only (AGENTS.md, docs/status.md).
  • Target: intridea/hashie at 9c81e8340d6b69940e14d8411f34a3efd7a6aa24 (261 subjects, 719 tests, 1,580 mutants).
  • Hardware: shared CI sandbox, 2 vCPU (x86_64), 2 GB RAM, Ubuntu 22.04.5, Ruby 3.4.3 (+PRISM). Absolute wall times are sandbox-specific; only same-box paired ratios are meaningful.
  • 30 runs: jobs in {1,2,6} x {baseline, candidate} x 5 pairs, AB/BA alternation (odd pairs baseline-first, even pairs candidate-first), serial under flock, cold cache (rm -rf .saboteur) per run.
  • Memory sampled every 0.3s across the whole process tree from /proc: RSS from status, PSS from smaps_rollup (falls back to RSS when unreadable). Peak over the run is reported. Wall is end-to-end run_one duration including the coverage-map build.

Host contention

The sandbox shares CPU with other tenants. Starvation windows show in the sampler cadence (healthy 0.3s per sample; starved over 1s per sample). Runs flagged contended (wall inflated, memory peaks unaffected): hashie-j2-baseline-1 (83s, borderline cadence 0.94s), hashie-j6-baseline-1 (273s), hashie-j1-candidate-2 (279s), hashie-j2-candidate-2 (261s), hashie-j6-candidate-2 (251s), hashie-j1-baseline-3 (292s), hashie-j1-candidate-3 (282s), hashie-j2-candidate-3 (275s), hashie-j6-candidate-3 (267s), hashie-j2-candidate-4 (580s), hashie-j6-candidate-4 (571s), hashie-j1-baseline-5 (594s), hashie-j1-candidate-5 (288s), hashie-j2-candidate-5 (268s), hashie-j6-candidate-5 (264s). Contended windows hit baseline and candidate slots both (order-bound, not variant-bound). Wall analysis uses clean runs and per-cell minimums; PSS and RSS peaks are valid in all windows.

Where mutineer won

At the measured versions. Not a statement about current releases.

  1. Lower peak memory in every pair measured.
  2. 20 change types with a switch to choose them; saboteur has one fixed set.
  3. CI features: baseline, score threshold, HTML report, GitHub Action with PR annotations, inline disable comments.
  4. A report of tests that never catch anything, and of redundant tests.
  5. No runtime dependencies.
  6. It refuses to score when a test file fails on its own. That blocked it on human-essentials, but it is a defensible safety rule.

Limitations

  • Results 1-5: one run per configuration, so no ranges and no repeatability numbers. Result 6 has 5 pairs per job level.
  • Rails apps were sampled: 3 lobsters models and 1 human-essentials model.
  • mutineer's fake kills were checked on 8 identical mutants, not a random sample, because its report names no killing test.
  • Only 3 real bugs, none detectable by either tool; 10 missed mutants per tool for usefulness.
  • Results 1-5 ran on macOS only; mutineer's Postgres failures may not occur on Linux.
  • Not measured: time to first missed mutant, diff-mode timing, database connections left after runs.
  • The author of this benchmark is also the author of saboteur.

Everything is in bench/vs-mutineer: the target commits and setup (PHASE0.md, PHASE1.md), the scripts (run_all, run_one), the raw JSON results and the full report (REPORT.md). Issues found in mutineer are written up in upstream-issues.md.
